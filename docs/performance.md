# 性能验证与容量规划

本页记录实际执行的控制面规模测试。完整业务基线为 100 个节点连接、100,000 个候选库存（其中 10,000 个活跃）、1,000 条规则、2 个共享数据库的控制面实例。活跃候选仍要求 30 秒内派发给 3 个不同代表节点；没有减少仲裁节点或延长周期来获得通过结果。当前生产数据库已改为 **MySQL 8.4**，SQLite 继续用于单机部署和测试。

**MySQL 8.4 最终无争用控制面规模复测已通过全部验收项**，实测结果见下文；此前失败报告继续保留。最终环境使用 512 MiB InnoDB 缓冲池，提交持久性保持 `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`。切换前的 PostgreSQL 历史结果单独记录。这些测试验证合成观测下的控制面链路，不能等同于 100 台公网主机的带宽、网络与长期稳定性认证。

## 可复现命令

需要仓库要求的 Go 工具链及单独用于测试的 MySQL 8.4 服务器。QA 账号需要创建、删除数据库及迁移权限；请勿使用生产服务器或生产 root 账号。测试总是创建随机 `newnexus_load_<随机值>` 数据库，使用生产迁移，不会复用或清空 URL 中已有数据库。`--cleanup` 在报告写出后只删除本次生成的数据库。不加该参数可保留现场，数据库名写在 JSON 的 `Schema` 字段，`Database` 和 `DatabaseVersion` 标识实际驱动及版本。普通生产服务不会创建任意数据库。

```sh
export NEWNEXUS_TEST_MYSQL='mysql://qa_user:qa_password@127.0.0.1:3306/qa_database?tls=false'
go run ./cmd/loadtest \
  --agents 100 --candidates 100000 --active 10000 --rules 1000 \
  --replicas 2 --batch 64 --db-connections 32 --dispatch-budget 32 \
  --duration 60s --drain 30s --cleanup \
  --output artifacts/mysql-performance.json
```

`--dispatch-budget 32` 是生产默认 `probe.concurrency`，没有为测试偷偷提高参数。候选批量导入和节点注册不计入 60 秒测量窗口；活跃候选初始均已到期，测试包含同时到期的冷启动负载。每条规则有 2 个目标、指定 2 个节点的组、2 节点仲裁，使用人工发布模式。测试不会访问 CDN、探测公共业务或调用 DNS 厂商写入接口。

复现最终成功结果时，MySQL 需设置 `innodb_buffer_pool_size=536870912`，保持 `innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`、binlog 开启。前八轮使用 128 MiB 缓冲池，第九轮及后续使用 512 MiB；数据库内存配置变化有原始记录，没有通过放松提交持久性获得成绩。具体容量仍需按目标生产工作集和总内存配置。

测试通过真实 Enroll/Connect gRPC 协议建立 100 条 loopback TCP 连接，在两个独立 Store、Hub、API 实例之间分配连接。两个实例通过生产数据库租约竞争运行 `API.StartWorkers`；调度、任务落库、结果上报、批量事务、聚合和规则评估都使用生产代码。每项合成结果有 3 个成功样本。60 秒到期后停止生成新的周期任务，最多再等 30 秒确认和排空既有任务。

每轮还会向两个 Hub 并发重放已经提交的结果，要求 raw metrics 增量为 0；随后构造真正首次写入的新任务和结果 ID，双实例同时提交，要求只增加唯一结果数且双方均能成功确认。这两项分别覆盖已提交结果重放和首次插入竞争。

任一确认完整性、活跃候选 30 秒覆盖、规则评估及健康收敛、幂等条件未达到，命令返回非零状态。不能只看是否生成了报告文件。

## 指标口径

- `ResultThroughputPerSecond` 只计算 60 秒计时窗口内收到 ACK 的结果，分母为实际计时秒数，不把排空阶段确认数算进吞吐。
- `ResultLoss` 是本轮截止时「已收到任务数减已确认结果数」，表示仍未确认的数量，**不代表已经证明发生永久数据丢失**。旧报告中的名称保留以便核对；正式 Agent 具有持久 outbox 和自动重连，合成负载客户端遇到流错误后会保留失败结果而不模拟整个磁盘恢复流程。
- `SchedulerCoverageWithin30Seconds` 要求同一个活跃候选在前 30 秒实际被至少 3 个不同节点收到，不能用仅创建任务或单节点覆盖代替。
- `TaskDeliveryP50MS/P95MS/P99MS` 从任务创建到客户端接收；`BatchAckP50MS/P95MS` 从结果批发送到收到匹配 ACK。它们不包含真实公网探测耗时。
- 新报告分别列出 `EvaluatedRules`（生产仲裁逻辑实际执行）、`RulesWithAllTargetSamples`（每条规则的两个目标都到达两个节点）、`HealthyRules`（评估后健康）。前几轮尚未分别记录前两项，表格没有把健康规则数冒充评估次数。
- `PeakHeapBytes` 与 `PeakProcessSysBytes` 来自 Go `runtime.MemStats`。后者是 Go 运行时向操作系统申请的内存，**不是进程 RSS**。同一个测试进程包含两个控制面实例及 100 个合成客户端，因此也不是单个服务副本内存。`SchemaBytes` 在 MySQL 下取 `information_schema.TABLES` 的数据及索引估算，不包含全局 redo、binlog、缓冲池等；PostgreSQL 历史报告取测试 schema 表及索引实际占用，两个值不能直接视为相同磁盘口径。
- 到期主动取消 worker 时，日志可能有 `context canceled` 的派发或扫描退出消息；结果流失败、未确认和未完成任务仍作为失败检查，不会因取消而被隐藏。

## 真实探测节点容量与未覆盖项目

真实 Agent 的速率限制单位是样本。默认每节点每秒 10 个样本，每任务 3 个样本时，100 个节点约为每秒 333 个任务的上限，尚未计算失败重试和带宽。

活跃候选最低样本率 = 活跃数 × 代表节点数 × 每任务样本数 ÷ 周期秒数。10,000 × 3 × 3 ÷ 30 = 3,000 样本/秒。1,000 条规则 × 2 目标 × 2 节点 × 3 样本 ÷ 30 = 400 样本/秒。两者均分到 100 节点已需至少每节点 34 样本/秒；还要为站点、库存发现、重试和调度不均留余量。

`NEWNEXUS_AGENT_RATE`、`NEWNEXUS_AGENT_CONCURRENCY`、任务下载前缀和周期应按照实际网络容量配置。每个 HTTP 样本下载 1 MiB 时，3,400 样本/秒理论上约需 3.32 GiB/秒总下行，不能忽略流量费用。提高速率本身不能保证较高 RTT 或低带宽节点及时完成任务。部署前需要真实分布式节点验证，参见 [Agent 部署文档](AGENT.md)。

本测试明确没有覆盖：

- 100 台真实主机、跨地域公网延迟、网络抖动、下载带宽与云厂商限速。
- TLS 的性能成本；协议证书校验、轮换、重启和撤销有独立真实 TLS/容器功能测试，但规模压测用 loopback 明文 gRPC。
- 独立进程/主机之间的控制面高可用和网络分区；本测试是同一进程内的独立实例共享数据库租约。
- DNS 厂商 API 限额、真正的 DNS 发布、自动切换外部写入和通知渠道吞吐。
- 合成客户端的磁盘 outbox 延迟、磁盘满、100 个真实节点进程的 CPU/内存，以及长时间（小时/天）稳定性。

应在目标生产硬件和网络上，使用同一完整规模参数完成无竞争的复测，再补真实节点、独立副本、厂商沙箱及长时间稳定性测试后决定生产容量。
